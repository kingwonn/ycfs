# M0-1 · 同步总线详细设计 + 可下单选型(铺量档 Contact-Go)

> 规格来源:data-product-spec.md 第四层 + route-03-pose-sync.md。
> 铺量档定位(PRODUCT-MATRIX.md 🅱):软件时间戳同步(ms 级,对 50Hz 动作够用),
> **不上硬件触发**(那是旗舰档,须换全局快门工业相机、抬 BOM)。
> 但即使软件同步,也要一个统一时钟主控把各流的时间戳锚到同一时基——这就是本总线。

## 一、架构决策:两档同步,本卡做铺量档

| | 铺量档(本卡) | 旗舰档(M0-1b,后续) |
|---|---|---|
| 同步方式 | MCU 统一时基 + 软件时间戳对齐 | MCU 硬件触发 + 曝光中点打戳 |
| 可达精度 | **1–5ms**(NTP 级) | **µs~sub-1ms** |
| 相机 | 消费级/USB 全局快门(可软触发) | 工业全局快门(外触发引脚) |
| 够不够 | 50Hz 动作 + 500Hz 力,ms 级对齐够(见 route-03 对 π0 亚毫秒的订正) | 高动态接触瞬态才需要 |

**为什么铺量档也要 MCU,而不是纯主机 NTP**:力传感 500Hz+、IMU 1kHz、相机 60fps
三个流若各自按主机时钟打戳,USB 传输抖动会带进几十 ms 误差。MCU 作**单一时基源**给
IMU/力/编码器同步采样并盖统一计数器戳,相机流事后按主机↔MCU 的对时偏移对齐——
把多流对齐从"几十 ms 不可控"压到"1–5ms 可测量、可写进证书"。

## 二、总线拓扑

```
          ┌─────────────── MCU (STM32G4, 主时基) ───────────────┐
          │  168MHz 系统时钟 → 32-bit 微秒计数器(单调,不回绕>1h)│
          │                                                      │
   ┌──────┴──────┐   ┌──────────┐   ┌───────────┐   ┌──────────┐│
   │ IMU (SPI)   │   │每指力×2   │   │夹爪编码器  │   │ LED 时标 ││
   │ 1kHz 采样   │   │(I2C/SPI) │   │(quad/SPI) │   │(GPIO)   ││
   │ 盖 µs 戳    │   │500Hz 盖戳 │   │200Hz 盖戳 │   │闪烁事件  ││
   └──────┬──────┘   └────┬─────┘   └─────┬─────┘   └────┬─────┘│
          └───────────────┴───────────────┴──────────────┘      │
                          │ USB CDC (带 MCU µs 戳的数据帧)       │
          ┌───────────────▼────────────────────────────────────┘
          │ 上位机(采集APP):对时握手(PTP-lite),把 MCU 戳映射到主机时钟
          │ 相机(USB/CSI 60fps):主机盖戳 + LED 时标交叉校准
          └── 落盘:所有流带【统一主机时基】戳 → LeRobot v3 打包
```

## 三、对时方案(软件档,ms 级,可测量)

1. **MCU 侧**:上电启动 32-bit µs 计数器;每个采样点(IMU/力/编码器)盖当前计数值。
2. **对时握手(PTP-lite)**:上位机每秒发 ping,MCU 回当前计数;记录 4 个时间戳
   (主机发/MCU 收/MCU 回/主机收),算偏移与往返延迟——与 NTP 同原理,LAN 内 1–2ms。
3. **相机对齐**:相机由主机盖戳(受 USB 抖动影响);用 **LED 时标**做交叉校准——
   MCU 控 LED 在已知 µs 闪烁,相机帧里出现的亮灭事件反推相机流的真实相位,
   把相机戳校准到 MCU 时基。**这是消费相机达到"帧内 ms 级"对齐的关键手段
   (route-03:GoPro 类无外触发,只能靠画面内 LED 频闪当公共时标)。**
4. **落盘**:所有流统一到主机时基,同步误差(P99)由 cert.py 的第 1 项实时算。

## 五、机器可查验收(本卡 done 的条件)

1. **BOM 总价** ≤ ¥150(同步总线子系统预算)—— bom.json 求和校验
2. **时基规格**:计数器 32-bit µs → 单调不回绕时长 ≥ 1h(2^32 µs ≈ 71 min,满足单条演示)
3. **对时方案可执行**:LED 时标交叉校准步骤完整(能测出相机流相对 MCU 时基的偏移)
4. **同步误差目标**:软件档 P99 ≤ 5ms(与 cert.py THRESHOLDS 一致,只紧不松)
5. **升级路径清晰**:旗舰档换外触发相机 + 触发线即达 sub-1ms,MCU/时基不变(不返工)

## 六、诚实边界

- 本卡是**设计 + 选型**,不是实物验证。P99≤5ms 是设计目标,实测需样机(M1 阶段)。
- LED 时标法的实际精度受相机帧率与快门类型限制:60fps 卷帘下,单次校准精度约
  "帧内 3–8ms"(route-03 已述),多次平均可收窄。这是消费相机的物理上限,不吹亚毫秒。
- 未解:USB CDC 在高负载(力 500Hz×2 + IMU 1kHz + 相机)下的带宽与丢帧率,需样机实测。

## 七、来源与推演依据(按用户引用纪律)

**第一性推演(理论依据):**
- "多流各自按主机时钟打戳→USB 抖动带进几十 ms" → 源自同步原理:软件时间戳精度受
  传输栈抖动主导,硬件时基才能压到 µs(route-03-pose-sync.md 组二,PTP vs NTP:
  软件戳无论 NTP/PTP 都只到 ms 级 [有据])。**推演**:故需 MCU 单一时基源盖统一计数戳。
- "统一时基把多流对齐从几十 ms 压到 1-5ms 可测量" → 由 N1(观察-动作时间对齐是标签保真前提,
  data-product-spec.md 第一层)推出:对齐误差 = 标签噪声,必须可测量并入证书。

**参考他家方案(引用 + 批判):**
- **LED 时标交叉校准**:参考 route-03 调查中 GoPro 无外触发时"画面内 LED 频闪当公共视觉时标"
  的做法([来源:joancharmant.com 卷帘测量 / Gyroflow rollingshutter,route-03 已引])。
  **批判**:该法精度受帧率/卷帘读出硬限,只到"帧内 ms",厂商若宣称亚毫秒即夸大——
  本设计因此只声称软件档 5ms,不吹 µs。
- **MCU 硬件触发方案(旗舰档参照)**:参考自研 STM32 触发板同相位多路脉冲 + 曝光中点打戳
  ([来源:route-03 组二,硬件同步论文 ResearchGate 387422847 / GrandTour 数据集 2602.18164])。
  **批判**:它能到 sub-1ms,但前置硬约束是相机须有外触发/全局快门,GoPro 类做不到——
  故只放旗舰档,不放铺量档(否则强迫换贵相机,违背铺量档成本定位)。
- **选型对标**:STM32G4 + ICM-42688-P 是开源 VIO/数采项目常见组合(route-03 中 Fast-UMI
  用 T265 板载 VIO 的替代路径)。**批判**:T265 已 EOL(route-03 [有据]),故不选现成模组,
  自研 MCU 时基更可控且不受停产影响——但代价是固件工作量,需 M1 实测验证带宽。
